## 📌 [Theme 1] 파이프라인 데이터 모델링 (`@dataclass`와 `Doc`)

* **골뱅이(`@`) 데코레이터와 `@dataclass`의 역할:**
  * 개발자의 반복적인 `__init__` 초기화 코드와 객체 출력(`__repr__`) 생성을 파이썬이 자동으로 대신해 주는 도구.
* **딕셔너리(`dict`) 대신 `Doc` 객체를 쓰는 이유:**
  * 오타 방지(버그 사전 차단), IDE 자동완성, **데이터와 행동(상태 변경 + 이력 기록)을 하나로 묶는 캡슐화**.
* **데이터 리니지(Lineage, 족보 추적):**
  * `doc.history`에 각 단계 통과 시각과 노트를 기록(`log`), 제외 사유(`exclude`), 실패 사유(`fail`)를 스스로 여권 도장처럼 들고 다님.

## 📌 [Theme 2] 무인 자동화 인프라와 관찰 가능성 (Observability)

* **`print()`를 넘어서는 모니터링 체계:**
  * 화면 출력은 세션이 끊기면 증발하므로, **영구 보존용 로그 파일(`pipeline.log`)**과 **즉각 알림용 웹훅(Slack/Teams)** 도입 필수.
* **실무 크론탭(Crontab) 설정 노하우:**
  * `0 3 * * 1` (매주 월요일 새벽 3시 배치).
  * `PATH`가 없는 크론 환경 특성상 **가상환경 파이썬 절대 경로** 필수 지정.
  * 표준 출력(1)과 에러 출력(2)을 한곳에 합쳐 기록: `>> /var/log/pipeline.log 2>&1`.

## 📌 [Theme 3] 멱등성(Idempotency)과 증분 처리(Incremental) & 버전 관리

* **증분 처리 (Incremental Batch):**
  * 규정 문서는 자주 안 바뀌므로, 매일 전체를 돌리는 대신 **`mtime`(수정시각)과 `file_hash`가 달라진 파일만 골라서 처리** (GPU 비용 90% 절감).
* **해시 눈사태 효과(오타 1자에 해시 전체 변경)와 버전 교체:**
  * 하드디스크에서는 파일이 **덮어쓰기**되지만, **DB 장부에는 과거 데이터가 남아있음**.
  * **파일명이 같을 때:** 기존 데이터의 스위치를 끄고(`is_current = False`, `indexed = False`), 새 데이터를 `True`로 올림.
  * **파일명이 바뀌었을 때 (`_최종.md` ➔ `_v2.md`):** **MinHash / 임베딩 유사도(95%+)**로 "이름만 바뀐 새 버전"임을 감지해 대체(`superseded_by`).
* **과거 원본 파일을 디스크(불변 저장소)에도 보관해야 하는 이유:**
  * 미래에 파서/모델 업그레이드 시 **재처리(Reprocessing)** 가능성 확보, 리니지 보존, 법적 감사(Audit) 증빙.
* **디스크엔 1개인데 `doc_id` 중복 게이트가 걸리는 이유 (방어적 프로그래밍):**
  * 주피터 셀 중복 실행, 재시도 코드 버그, 바로가기(심볼릭 링크)로 동일 원본 중복 읽기, 리눅스 상의 NFD/NFC 파일 공존 후 파이썬 정규화 충돌 등.

## 📌 [Theme 4] 텍스트 품질 검사와 "2중(캐스케이드) 필터링"

* **모지바케(`뷁뛝뺋` 외계어) 처리:**
  * **1단계:** 인코딩 감지(`charset_normalizer`) 및 CP949 재시도로 복구.
  * **2단계:** 미복구 시 품질 지표 미달로 격리 큐(DLQ, `./quarantine/`)로 이동 (영구 삭제 X ➔ 나중에 OCR 2차 재시도 경로 확보).
* **'뷁'도 유니코드상 한글(`[가-힣]`, 11,172자)로 잡히는 함정:**
  * 단순 정규식은 외계어 한글도 100% 한글로 오판함.
  * **해결:** 일상에서 쓰는 **상용 한글 2,350자(KS X 1001)** 대조 또는 **한국어 형태소 분석기(Kiwi)**의 문법성 채점으로 분별.
* **토크나이저 vs 파이썬 전처리 라이브러리:**
  * LLM 토크나이저(BPE)는 쓰레기도 바이트로 쪼개 통과시키는 단순 기계이므로, **앞단의 파이썬 라이브러리(`ftfy`, `kiwi`, 정규식)가 수문장 역할**을 해야 함.
* **2중 검사 시스템 (Cascade Filtering):**
  * **1차 (초고속 파이썬 규칙, 0.001초):** 길이, 정규식 PII(전화번호), 상용한글 대조 ➔ 명백한 쓰레기 80%를 비용 0원으로 광속 탈락.
  * **2차 (소형 AI/NLP 모델):** 문맥 기반 인명(NER) 마스킹, 문법성 채점 ➔ 까다로운 문맥만 정밀 타격.

## 📌 [Theme 5] 트랙 1 & 트랙 5 핵심 실습 요약

* **트랙 1 (게이트 경보 3단계 분류 및 자동 승격):**
  * **하드 게이트(비상정지):** 출력이 0건(`n_out == 0`, 인덱스 백지화 위험), `doc_id` 중복 등 치명적 사고 차단.
  * **소프트 게이트(경고등):** 사소한 몇 건의 파싱 실패(`n_failed > 0`) 등은 기록만 남기고 파이프라인 지속.
  * **경보 3단계:** 즉시(새벽 비상벨) / 아침요약(출근 후 커피 타임 확인) / 기록만.
  * **승격(Promotion):** 소프트 경고가 **3회 연속(`streak >= 3`)** 발생하면 구조적 결함으로 판단하여 하드 게이트로 승격 제안.
* **트랙 5 (Qdrant ACL 기반 역할별 권한 검색):**
  * 사내 RAG의 기밀/인사평가 유출 방지.
  * **사전 필터링 (`MatchAny(any=allowed)`):** 권한이 허용된 문서들만 골라낸 뒤 그 안에서 코사인 유사도 검색.
  * **실측 결과:** 동일 검색어(`"인사평가 결과"`) 질의 시,
    * 일반 사원(`employee`) / 팀장(`manager`) ➔ **유출 0건** (공용 예산 문서로 안전 대체 노출)
    * 인사 담당자(`hr_admin`) ➔ 기밀 인사평가 문서 **1등(Hit@1) 적중**.

## 📌 [Theme 6] 라마인덱스(LlamaIndex) vs 랭체인(LangChain)

* **랭체인 (LangChain):**
  * **"만능 오케스트라 지휘자"**
  * 외부 API 연동, 챗봇 대화 흐름, LangGraph를 활용한 복합 멀티 에이전트 워크플로우에 최적화.
* **라마인덱스 (LlamaIndex):**
  * **"전문 데이터 사서"**
  * 고성능 RAG, 정밀한 문서 인덱싱, 계층적 색인, 복잡한 표/PDF 파싱(`LlamaParse`)에 압도적 특화.
* **실무 정석 (하이브리드):**
  * 검색/색인 엔진(Retriever)은 **라마인덱스**로 깎고, 비즈니스 로직과 에이전트는 **랭체인**으로 감싸서 배포.
