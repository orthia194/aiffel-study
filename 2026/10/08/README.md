>혼자 공부할 때는 리더보드 순위가 높고 똑똑한 모델(예: Qwen, Llama 등)을 자유롭게 쓰면 되지만, **실제 프로젝트나 회사 업무에서는 “성능이 좋다고 무조건 쓸 수 있는 것”이 아닙니다.**

### 1. 법적으로 되나? (라이선스) — *법무팀의 관심사*
가장 먼저 걸러내야 하는 절대적인 1차 필터입니다. 상업적 이용이 불가능하다면 아무리 뛰어난 모델이라도 회사 서비스에 탑재할 수 없습니다.

* **상업적 이용 가능 여부:** 
  * `Apache 2.0`, `MIT`: 제약이 거의 없어 기업에서 가장 선호합니다.
  * 독자 라이선스: MAU(월간 활성 사용자 수) 제한이 있거나(예: Llama의 7억 명 제한), 파생 모델 공개 의무, 별도 승인 필요 여부 등을 확인해야 합니다.
  * *참고(Qwen의 경우):* Qwen 2.5의 대부분 모델은 `Apache 2.0`으로 개방되어 실무 라이선스 통과율이 높지만, 특정 대형 크기나 파생 모델은 개별 라이선스 조항을 확인해야 합니다.
* **학습 데이터 저작권 이슈:** 모델 개발사가 학습에 사용한 데이터에 저작권 분쟁 소지가 없는지 확인합니다.



### 2. 우리 서버에 올라가나? (인프라 및 리소스) — *인프라팀의 관심사*
우리 팀/회사가 보유한 GPU 장비나 예산 범위 내의 클라우드 서버에서 실제로 안정적으로 구동되는지 확인해야 합니다.

* **모델 크기와 VRAM(GPU 메모리) 요구량:**
  * 모델 파라미터 수(7B, 14B, 32B, 72B 등)에 따라 필요한 VRAM이 급격히 증가합니다.
  * 단순히 모델을 올리는 것뿐만 아니라, 서빙 프레임워크(vLLM, Ollama, TGI 등)와 동시 접속자(동시 요청 배치), 긴 컨텍스트 윈도우(KV Cache)를 감당할 VRAM 여유가 있는지 계산해야 합니다.
* **양자화(Quantization) 지원:** FP16/BF16 대신 4-bit(AWQ, GPTQ), 8-bit 등으로 경량화했을 때 성능 저하 없이 우리 장비에 올라가는지 확인합니다.
* **추론 속도(Latency)와 처리량(Throughput):** 사용자가 체감하기에 응답 지연(TTFT, Time to First Token)이 너무 길지 않은지 검토합니다.



### 3. 한국어가 되나? (언어 및 토크나이저 효율) — *기획/개발팀의 관심사*
다국어 모델이라도 한국어 처리 효율과 문맥 이해도가 떨어지면 사용하기 어렵습니다.

* **한국어 표현력 및 문맥 이해:** 어색한 번역투가 없는지, 한국 문화·법률·도메인 고유명사를 제대로 이해하는지 봅니다.
* **토크나이저(Tokenizer) 효율 (압축률):**
  * 한국어 1글자가 몇 개의 토큰으로 쪼개지는지 확인해야 합니다.
  * 토크나이저가 한국어를 비효율적으로 쪼개면 **추론 속도가 느려지고, 한 번에 처리할 수 있는 글자 수가 줄어들며, API 사용 시 비용이 배로 증가**합니다.
  * *(Qwen의 강점 중 하나가 어휘집(Vocab size)이 커서 동양권 언어의 토큰 압축률이 우수하다는 점입니다.)*



### 4. 성능 (태스크 적합도) — *앞의 3가지를 통과한 후보끼리의 경쟁*
**성능은 1~3번을 통과한 후보들 중에서 비교**하는 것입니다. 일반 벤치마크 숫자(MMLU 등)보다 **우리가 만들려는 기능에 맞는 실질적 성능**이 중요합니다.

* **우리의 주 목적(Task)에 맞는 역량:**
  * RAG(검색 증강 생성): 문맥 참조 능력, 환각(Hallucination) 억제력
  * 에이전트/자동화: Function Calling(Tool Use), 구조화된 출력(JSON/YAML) 생성 능력
  * 코딩/추론: 수학적 논리, 코드 생성 정확도
* **자체 평가 셋(Eval Set) 검증:**
  * 공개 벤치마크 점수만 믿지 않고, 실제 서비스에서 발생할 예상 질문 50~100개를 뽑아 정답률을 직접 블라인드 테스트해 봅니다.



### 5. 얼마나 드나? (비용 및 TCO) — *의사결정권자의 관심사*
상용 API(OpenAI, Claude 등)를 쓰는 것과 오픈소스 모델(Qwen 등)을 자체 서버에 띄우는 것 중 어느 쪽이 경제적인지 비교합니다.

* **API vs 자체 호스팅(On-Premise/Cloud GPU) 비교:**
  * 트래픽이 적을 때는 종량제 API가 훨씬 저렴합니다.
  * 트래픽이 일정 수준 이상으로 많아지거나 내부 보안 규정(망분리)이 필수라면 자체 호스팅이 유리합니다.
* **총소유비용(TCO, Total Cost of Ownership):**
  * 단순히 GPU 대여료뿐만 아니라 인프라 유지보수 인력, 서버 가동 전력, 모니터링 구축 비용까지 고려해야 합니다.


### 💡 실무 관점에서 Qwen을 바라본다면?

공부할 때 쓰셨던 **Qwen(특히 Qwen 2.5 라인업)**은 실무 후보군으로도 매우 강력한 편입니다.
1. **라이선스:** 대다수 모델이 Apache 2.0으로 상업적 도입이 매우 쉬움
2. **서버 적합성:** 0.5B부터 72B까지 크기가 세분화되어 있어 인프라 사양에 맞춤 선택 용이
3. **한국어/토크나이저:** 다국어 어휘집이 매우 커서 한국어 토큰 압축률과 표현력이 글로벌 오픈소스 중 상위권
4. **성능:** 코딩, 수학, Function Calling, 긴 문맥 처리 능력이 우수

따라서 실무 보고서를 작성하실 때는 **"Qwen이 성능이 좋아서 골랐습니다"**가 아니라, **"1) 상업용 무료 라이선스이며, 2) 보유 중인 GPU 사양에서 양자화 서빙이 가능하고, 3) 한국어 토큰 효율이 높아 타 모델 대비 응답 속도 및 비용 면에서 유리하여 최종 선정했습니다"**와 같이 5가지 기준을 순서대로 통과한 근거를 들어 설명하시면 됩니다.



### 1. 사진 핵심 내용 요약

* **이름 표기법:** `Qwen...-397B-A17B`처럼 숫자가 2개인 모델은 MoE 구조입니다.
  * **397B (총 파라미터):** 모델이 가진 전체 지식의 양 (전체 캐비닛 크기)
  * **A17B (활성 파라미터, Active):** 토큰 1개를 생성할 때 실제로 계산에 참여하는 파라미터 (열어보는 서랍 수)
* **단 하나의 판단 공식:**
  * **GPU 메모리(VRAM) 요구량 = 총 파라미터 기준** (397B 전체가 GPU에 상주해야 함)
  * **계산량 및 추론 속도 = 활성 파라미터 기준** (17B만큼만 계산하므로 매우 빠름)
* **실무적 주의점:** 
  * "A17B니까 17B짜리 가벼운 모델이네!" 하고 GPU를 1장만 잡으면 **메모리 부족(OOM)**으로 모델 자체가 올라가지 않습니다.



### 2. Dense vs MoE 구조 비교

| 비교 항목 | Dense (밀집 모델) | MoE (전문가 혼합 모델) |
| :--- | :--- | :--- |
| **작동 방식** | 모든 토큰을 처리할 때 **모든 뉴런(파라미터)이 전부 참여** | 라우터(Router)가 질문을 보고 **특정 전문가(Expert) 몇 개만 켜서 참여** |
| **비유** | 만능 박사 1명이 모든 질문에 혼자 머리를 쥐어짜며 답함 | 도서관(전체 지식)에서 질문에 맞는 사서 2~3명만 뽑아 답을 찾게 함 |
| **GPU 메모리 요구량 (VRAM)** | 파라미터 크기만큼만 필요 (예: 30B 모델 = 30B 메모리) | **총 파라미터 크기만큼 대량 필요** (예: 30B 중 3B만 켜도 30B 메모리 필요) |
| **추론 속도 (Latency)** | 파라미터가 클수록 연산량이 많아 속도가 느림 | 전체 지식량 대비 **연산량이 매우 적어 속도가 훨씬 빠름** |
| **처리량 (Throughput)** | 동시 요청이 몰리면 GPU 연산 부담 급증 | 활성 연산량이 적어 **동시 요청(배치)을 훨씬 많이 소화 가능** |
| **대표 예시** | Llama 3 8B/70B, Qwen 2.5 7B/14B/32B/72B | Mixtral 8x7B/8x22B, DeepSeek-V2/V3, DBRX |



### 3. 어떤 상황에 무엇을 써야 할까? (실무 선택 가이드)

#### 🟢 Dense 모델을 선택해야 하는 상황
> **"인프라(GPU) 자원이 제한적이고, 1~2대의 GPU로 단일 작업을 안정적으로 돌릴 때"**

1. **GPU 장비가 1장(또는 소형 서버)뿐일 때:**
   * 보유한 VRAM이 16GB, 24GB(예: RTX 3090/4090, L4) 수준이라면 MoE는 모델 자체가 메모리에 다 안 들어갑니다. Dense 7B, 14B 모델을 양자화하여 올리는 것이 훨씬 현실적입니다.
2. **단말기/온디바이스(Edge) AI 구축 시:**
   * 스마트폰, 로컬 PC, 임베디드 기기는 메모리 대역폭과 용량이 제한되므로 작은 Dense 모델(3B, 7B 등)이 유리합니다.
3. **파인튜닝(추가 학습)을 많이 해야 할 때:**
   * MoE는 전문가 모듈 간의 라우팅 불균형 문제 등으로 인해 Dense 모델보다 LoRA/Full 파인튜닝 난이도가 높고 하이퍼파라미터 튜닝이 까다롭습니다.



#### 🔵 MoE 모델을 선택해야 하는 상황
> **"GPU 메모리(VRAM)는 넉넉하고, 대규모 트래픽을 빠른 속도로 소화해야 할 때"**

1. **동시 사용자(트래픽)가 많은 대규모 상용 서비스:**
   * 사용자가 많을 때는 계산량(FLOPs) 병목이 생깁니다. MoE는 토큰당 연산 비용이 낮아 동일 시간 동안 처리할 수 있는 사용자 요청 수(Throughput)가 압도적으로 높습니다.
2. **응답 지연 시간(Latency)이 매우 중요한 실시간 서비스:**
   * 70B급의 똑똑한 두뇌 성능을 원하지만, 70B Dense 모델은 응답 생성 속도가 너무 느려서 챗봇 체감 품질이 떨어질 때 MoE(예: 총합은 70B급이지만 활성은 10~15B급인 모델)를 쓰면 **높은 지능 + 빠른 속도**를 동시에 잡을 수 있습니다.
3. **엔터프라이즈급 GPU 인프라(A100/H100 멀티 노드)를 갖추고 있을 때:**
   * "메모리를 선불로 내고 속도를 산다"는 말처럼, 이미 VRAM 풀(Pool)이 넉넉한 환경에서는 Dense보다 MoE를 서빙하는 것이 서버 효율 대비 성능이 극대화됩니다.



### 💡 한 줄 요약
> **인프라 예산이 적고 GPU가 1~2장뿐이라면 `Dense` 모델**을 고르고,  
> **서버 VRAM이 넉넉하고 빠른 응답 속도와 다중 사용자 처리가 필요하다면 `MoE` 모델**을 고르는 것이 정답입니다.

> 실제로 모델을 띄워 서비스할 때 VRAM은 크게 **① 모델 가중치(Weights)**뿐만 아니라 **② KV 캐시(KV Cache)**, **③ 활성화 텐서(Activation Memory)**, **④ 서빙 프레임워크 오버헤드(CUDA 런타임 등)**까지 모두 합친 공간을 차지하기 때문입니다.  
> 회의실에서 5초 만에 암산하는 법부터, 실제 서비스 환경에서 왜 훨씬 더 많은 VRAM이 필요한지 알기 쉽게 정리해 드립니다.  

### 1. [1단계 암산법] 모델 가중치(Weight) 메모리 계산

모델을 GPU에 얹기만 할 때 필요한 순수 기본 메모리입니다.
비트(Bit)와 바이트(Byte)의 관계(`1 Byte = 8 Bit`)만 알면 바로 계산됩니다.

* **FP16 / BF16 (기본 정밀도, 16비트 = 2바이트):**
  * 공식: $\text{파라미터 수(B)} \times 2\text{ GB}$
  * 예: 7B 모델 $\approx$ **14 GB**, 32B 모델 $\approx$ **64 GB**, 70B 모델 $\approx$ **140 GB**
* **8-bit 양자화 (INT8, 8비트 = 1바이트):**
  * 공식: $\text{파라미터 수(B)} \times 1\text{ GB}$
  * 예: 7B 모델 $\approx$ **7 GB**, 32B 모델 $\approx$ **32 GB**, 70B 모델 $\approx$ **70 GB**
* **4-bit 양자화 (INT4, 4비트 = 0.5바이트) — *사진에 나온 "절반의 법칙":***
  * 공식: $\text{파라미터 수(B)} \times 0.5\text{ GB}$
  * 예: 7B 모델 $\approx$ **3.5 ~ 4 GB**, 14B 모델 $\approx$ **7 GB**, 32B 모델 $\approx$ **16 GB**, 70B 모델 $\approx$ **35 ~ 40 GB**

> **💡 회의용 퀵 공식:**  
> "4비트로 줄이면 파라미터 수의 딱 **절반(0.5배)**, 16비트 원본이면 **2배**를 GB로 생각하면 끝납니다."


### 2. 그런데 왜 상상보다 훨씬 더 많은 VRAM이 필요할까?

서버에 모델만 올려두고 아무 말도 안 시킬 게 아니라면, **추론을 시작하는 순간 추가 메모리가 폭발적으로 늘어납니다.**

#### ① KV 캐시 (KV Cache) — "대화가 길어지고 사람이 많아질수록 기하급수적으로 증가"
LLM은 다음 단어를 예측할 때 앞서 나온 모든 단어(질문 + 이전 답변)의 Key/Value 벡터를 다시 계산하지 않기 위해 메모리에 적재(캐싱)해 둡니다.

* **계산 공식:**
  $$\text{KV 캐시 메모리} \approx 2 \times (\text{레이어 수}) \times (\text{KV 헤드 수} \times \text{헤드 차원}) \times (\text{컨텍스트 길이}) \times (\text{정밀도 바이트}) \times (\text{동시 접속자 수})$$
* **왜 무서울까요?**
  * 예를 들어 Llama 3 70B 모델에서 긴 문서(128k 컨텍스트)를 읽히면, **사용자 단 1명의 대화 기록(KV 캐시)만으로도 약 10~20GB 이상의 VRAM**을 먹습니다.
  * 만약 이 긴 문서를 **동시에 4명이 요청하면? KV 캐시만으로 60~80GB가 필요**해져서 A100(80GB) 1장으로는 모델을 띄우지도 못하고 터집니다.

#### ② 활성화 메모리(Activation) & 임시 버퍼
* 입력된 토큰이 모델의 수십 개 레이어를 통과하며 행렬 곱셈을 할 때 생기는 중간 연산값입니다. 
* 한 번에 처리하는 문장이 길수록(Batch size $\times$ Sequence length) 커집니다.

#### ③ 서빙 프레임워크 기본 예약분 (vLLM 등)
* vLLM 같은 고성능 서빙 엔진은 속도 최적화를 위해 시작할 때 사용 가능한 **VRAM의 90%(기본값 `gpu_memory_utilization=0.9`)를 미리 통째로 잡아둡니다.** 
* 모델 가중치를 채우고 남은 공간을 전부 KV 캐시 블록(PagedAttention)으로 사전 할당해 두기 때문입니다.


### 3. 실무 종합: 실제 필요한 VRAM 한눈에 계산하기

실무에서는 **"모델 가중치만 딱 맞춰서" GPU를 사면 100% 장애가 발생**합니다. 아래와 같은 **안전 여유율(Safety Margin)**을 두어야 합니다.

| 상황 | 필요한 총 VRAM 산출 기준 | 예시 (14B 모델 4-bit 양자화 기준) |
| :--- | :--- | :--- |
| **개인 공부 / 단일 테스트** (1명 사용, 짧은 대화) | `모델 가중치 + 2~4 GB` | 가중치 7GB + 여유 3GB = **약 10 GB** (RTX 3060 12GB로 가능) |
| **소규모 사내 챗봇** (동시 3~5명, 일반 대화 4k) | `모델 가중치 × 1.3 ~ 1.5배` | 가중치 7GB × 1.5 = **약 11~15 GB** (RTX 4090 24GB 추천) |
| **실무 서비스 / RAG** (동시 다발 요청, 긴 문서 참조 16k+) | `모델 가중치 × 2배 이상` | 가중치 7GB + 대용량 KV 캐시 = **20~30 GB 이상** (A10G 24GB 또는 A100 필요) |



### 📌 결론 및 핵심 요약

1. **모델 가중치 암산:** 4비트 양자화 기준 **"파라미터 수 $\times$ 0.5 GB"**로 3초 만에 계산합니다.
2. **실제 서비스 VRAM:** "추론 속도를 내기 위한 **KV 캐시**는 `(동시 사용자 수) × (문맥 길이)`에 비례해서 무섭게 불어난다"는 점을 반드시 감안해야 합니다.
3. 따라서 인프라팀에 스펙을 요구할 때는 **"모델 크기가 16GB니까 24GB GPU 1장이면 됩니다"가 아니라, "동시 접속자와 RAG 문서 길이에 따른 KV 캐시까지 고려해 최소 32GB~40GB 이상의 VRAM 풀이 필요합니다"**라고 답하는 것이 정답입니다.

### 1. 양자화의 좋은 점 (얻는 것)

#### ① VRAM(메모리) 요구량의 획기적 절감 (가장 큰 이유)
* 원본 16비트(FP16/BF16) 대비 **4비트 양자화 시 메모리를 약 1/3 ~ 1/4 수준(0.5배 법칙)**으로 줄일 수 있습니다.
* **실무적 이점:** 
  * 수천만 원짜리 고가 서버 GPU(A100/H100) 대신, 일반 상용 GPU(RTX 3090/4090)나 저렴한 클라우드 인스턴스로도 대형 모델을 올릴 수 있어 **인프라 비용이 극적으로 절감**됩니다.

#### ② 추론 속도 및 처리량(Throughput) 향상
* LLM 추론은 GPU의 연산 속도보다 **메모리에서 가중치를 읽어오는 대역폭(Memory Bandwidth)이 병목(Memory-bound)**인 경우가 많습니다.
* 가중치 용량이 1/4로 줄어들면, 메모리에서 GPU 코어로 데이터를 퍼 올리는 속도가 빨라져 **토큰 생성 속도(Tokens/sec)가 빨라집니다.**

#### ③ 로컬 환경 및 CPU 구동 가능 (GGUF의 경우)
* 자료에 언급된 `GGUF` 방식을 쓰면 GPU가 아예 없거나 VRAM이 부족한 개인 노트북, 맥북(Apple Silicon), CPU 환경에서도 LLM을 돌려볼 수 있습니다.



### 2. 양자화의 나쁜 점 (내주는 것 / 잃는 것)

숫자의 정밀도(소수점 자리)를 16비트에서 4비트로 뭉뚱그려 줄이는 것이기 때문에 필연적으로 **"정밀한 연산 능력의 저하"**가 발생합니다.


#### ① 특정 작업(Task)에서의 품질 저하 (망가지는 순서)
* **일상 대화, 단순 요약, 분류:** 4비트로 줄여도 큰 차이를 체감하기 어렵습니다. (상대적으로 안전)
* **정해진 형식 출력 (JSON, YAML 등):** 
  * 괄호를 닫지 않거나 따옴표가 누락되는 문법 에러가 잦아집니다.
* **복잡한 추론 및 수학/코딩 (다단계 추론):** 
  * 단계별로 발생하는 미세한 오차가 누적되어 최종 답이 틀릴 확률이 높아집니다.
* **함수 호출 (Function Calling / Tool Use):** 
  * AI 에이전트 구축 시 도구 이름이나 인자(Parameter)를 엉뚱하게 넘기는 실패율이 증가합니다.

#### ② 언어별 손실 격차 (한국어 등 비영어권 언어)
* 많은 양자화 캘리브레이션(보정) 데이터셋이 영어 위주로 되어 있어, **영어보다 데이터 비율이 적은 한국어·다국어 표현력, 맞춤법, 미묘한 뉘앙스 처리가 먼저 무너질 수 있습니다.**

#### ③ 호환성과 파이프라인 관리 복잡도 증가
*  `GGUF`, `AWQ`, `GPTQ` 등 형식마다 구동 도구(런타임)가 다릅니다.
  * 개발/테스트할 때 쓰던 형식(GGUF / Ollama)과 실제 운영 서버 배포용 형식(AWQ / vLLM)이 달라 **중간에 모델을 다시 다운로드하거나 변환해야 하는 번거로움**이 생깁니다.
