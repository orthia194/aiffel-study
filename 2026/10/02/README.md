### 단일 단계 에이전트 (Single-step Agent)

* **핵심 동작:** 입력이 오면 **단 한 번만 도구(Tool)를 선택하거나 호출**하고 즉시 응답을 생성합니다.
* **특징:** 루프(Loop)나 피드백 과정이 없습니다. 질문을 받고 "아, 이 도구 쓰면 되겠네" 하고 1회 호출 후 끝내는 가장 단순한 형태입니다.
* **비유:** 질문하면 계산기 버튼 한 번 누르고 답을 바로 말해주는 상황.

### 사고의 사슬형 에이전트 (Chain-of-Thought Agent / ReAct 등)

* **핵심 동작:** **`생각(Think) -> 행동(Act/도구 사용) -> 관찰(Observe)`** 패턴을 단계별로 차근차근 이어나가는 에이전트입니다.
* **특징:** 도구를 한 번 실행한 결과(관찰)를 보고, 그 다음 행동을 추론(Thought)하면서 한 단계씩 목표에 접근합니다. 어제 다루었던 가장 전형적인 에이전트 동작 루프 형태입니다.
* **비유:** 문제 풀이 과정을 연습장에 한 줄씩 써가면서 차근차근 답을 찾아가는 상황.

### 계획-실행형 에이전트 (Plan-and-Act Agent)

* **핵심 동작:** 일을 시작하기 전 먼저 **전체 계획(Sub-goal 목록)을 수립**한 뒤, 계획된 순서대로 도구들을 순차 실행합니다.
* **특징:** 사고의 사슬형(CoT)이 "다음 1걸음만 생각하는 방식"이라면, 이 방식은 "전체 1~5단계 로드맵을 먼저 그리고 시작하는 방식"입니다. 실행 도중 중간 결과가 안 좋으면 계획을 재수정(Re-planning)하기도 합니다.
* **비유:** 여행 가기 전에 1일 차, 2일 차 상세 일정표를 먼저 짜고 하나씩 지워가며 여행하는 상황.

### 반추·자기 개선형 에이전트 (Reflective / Self-improving Agent)

* **핵심 동작:** 결과를 만들어낸 후, **"내가 작성한 결과물이 유저의 요구에 부합하는가?"를 스스로 비판(Critique)하고 검토하여 수정**합니다.
* **특징:** `생성 노드 -> 검수/비평 노드 -> 수정 노드`의 피드백 루프가 워크플로우 내에 존재합니다. 코드를 짜고 스스로 테스트 케이스를 돌려본 뒤, 에러가 나면 스스로 수정해서 완벽한 코드를 제출하는 방식입니다.
* **비유:** 글을 작성한 뒤 바로 제출하지 않고, 스스로 채점관 역할을 하며 다듬고 수정하여 최종 제출하는 상황.

### 재귀 분해형 에이전트 (Recursive Decomposition Agent)

* **핵심 동작:** 너무 거대하고 복잡한 문제를 만나면, 이를 **작은 하위 문제(Sub-problem)들로 쪼개고(Decompose)**, 필요하다면 또 그 하위 문제를 더 작은 문제로 쪼개어 각각을 해결한 뒤 합치는 방식입니다.
* **특징:** 복잡한 오케스트레이션(Orchestration)이나 다중 에이전트(Multi-agent) 시스템에서 많이 쓰입니다. 메인 에이전트가 하위 에이전트들에게 일을 나눠주고 결과를 취합하는 구조입니다.
* **비유:** "회사 하나 차려줘"라는 거대한 요청을 받았을 때 개발, 마케팅, 재무 팀으로 나누어 업무를 위임하고 나중에 합치는 상황.

# 📌 MCP (Model Context Protocol)

## 1. 개요 (What is MCP?)

* **정의:** AI 모델(LLM)과 외부 데이터/도구(GitHub, Notion, 로컬 파일 시스템 등)를 연결하는 **표준 개방형 프로토콜(Interface Standard)**.
* **핵심 역할:** 컴퓨터의 'USB-C 포트'처럼, AI가 다양한 외부 시스템과 통신할 때 사용하는 **'표준 어댑터'** 역할을 수행.
* **개발사:** Anthropic (2024년 11월 오픈소스로 공개)

---

## 2. 등장 배경 (Why MCP?)

### ❌ MCP 이전 ($M \times N$ 문제)

* 각 AI 모델(Claude, GPT, Gemini 등)마다 외부 서비스(GitHub, Slack, DB 등)를 연동하려면 전용 연결 코드(Custom Integration)를 개별 작성해야 했음.
* 연동 대상이 늘어날수록 커넥터의 수가 폭발적으로 증가 ($M$개의 AI $\times$ $N$개의 서비스 = $M \times N$).

### ⭕ MCP 이후 ($M + N$ 연동)

* **표준 규격 통일:** 개발자는 자사 서비스용 **MCP Server** 하나만 구축해 두면 끝.
* MCP를 지원하는 모든 AI 앱/클라이언트($M$)가 하나의 MCP 서버($N$)에 즉시 연동되어 연동 복잡도가 $M + N$으로 획기적으로 줄어듦.

---

## 3. 핵심 아키텍처 (Client - Server Structure)

MCP는 **JSON-RPC 2.0** 기반의 클라이언트-서버 구조로 동작합니다.

```
[ MCP Host (Claude Desktop, Cursor IDE 등) ]
                      │
                (MCP Client)
                      │  <-- 표준 MCP 프로토콜
                      │
                (MCP Server)
                      │
  [ 외부 시스템 / 데이터 (GitHub, DB, 로컬 파일 등) ]

```

1. **MCP Host (앱):** Claude Desktop, Cursor, VS Code 등 AI를 활용하는 실행 프로그램.
2. **MCP Client:** Host 내부에서 MCP Server와의 연결 및 통신을 담당하는 주체.
3. **MCP Server:** 특정 서비스/데이터에 대한 접근 권한과 기능(도구)을 표준 규격으로 감싸 제공하는 프로그램.
* **로컬 MCP 서버 (Local):** 내 PC 내의 파일, SQLite DB, 로컬 터미널 명령 등 연동.
* **원격/외부 MCP 서버 (Remote):** GitHub, Notion, Figma, Slack 등 Cloud API 연동.



---

## 4. MCP 서버가 AI에게 제공하는 3가지 요소

| 기능 (Capability) | 설명 | 활용 예시 |
| --- | --- | --- |
| **Tools (도구)** | AI가 실제 실행(Action)할 수 있는 기능 | `create_issue`, `send_slack_message`, `query_db` |
| **Resources (자원)** | AI가 읽을(Read) 수 있는 데이터/콘텐츠 | 파일 내용, 데이터베이스 테이블, API 응답 |
| **Prompts (프롬프트)** | 사전 정의된 표준 작업 템플릿 | `code_review_prompt`, `summarize_notes` |

---

## 5. 핵심 장점

* **재사용성 및 확장성:** 한 번 만든 MCP 서버는 어떤 MCP 클라이언트(Cursor, Claude 등)에서도 재사용 가능.
* **보안 및 통제력:** 로컬 환경에서 MCP 서버를 실행하여 민감한 개인 데이터/파일이 외부에 무단 노출되는 것을 방지.
* **Agentic AI 구축의 핵심 부품:** 자율적 에이전트가 현실 세상의 앱들과 소통할 수 있는 가장 강력하고 표준적인 창구.

| --- | --- | --- | --- |
| **위치** | 최상위 애플리케이션 (사용자/AI 제어부) | 호스트 **내부**에 존재하는 통신 모듈 | 독립적으로 실행되는 서비스/데이터 감싸기(Wrapper) |
| **주요 역할** | • 사용자 및 LLM 관리 |  |  |



• 실행 승인 & 보안 감사(Audit)

• 메시지 전달 및 에러 처리



• 표준 규격(SDK) 통신 담당 | • 실제 기능/데이터(도구, 파일, DB) 제공



접근 권한 검증 및 서버 로그 기록 |
| **비유** | **회사 사장님 (최종 결정권자)** | **전담 비서 / 통역관** | **외부 전문 외주업체** |
| **실제 예시** | Cursor IDE, Claude Desktop, **개발자가 직접 만든 에이전트** | Host 코드 내의 MCP Client 객체 | GitHub MCP 서버, SQLite MCP 서버, File System MCP 서버 |

---

## 2. 핵심 동작 및 아키텍처 원리

### 1) 통신 흐름 (LLM과 서버는 직접 만나지 않는다)

```
[ 사용자 ] ───> [ 호스트 (Host) ] ◄─── (판단 요청/응답) ───► [ LLM (모델) ]
                     │
              (호스트 내부)
                     │
              [ 클라이언트 (Client) ] 
                     │
       ◄─── (표준 MCP 프로토콜 통신) ───►
                     │
              [ 서버 (Server) ] ───> [ 실제 시스템 (DB, GitHub, 파일 등) ]

```

* **LLM은 서버와 직접 대화할 수 없습니다.**
* LLM이 "A 도구를 실행해 줘"라고 요청하면, **호스트**가 그 요청을 검토/승인한 뒤 **전담 클라이언트**를 시켜 **서버**로 전달합니다.
* **이점:** 중앙 통제관인 호스트가 중간에서 **"어떤 에이전트가 어떤 도구를 썼는지"** 한곳에서 기록하고 통제(감사/승인)할 수 있습니다.

---

### 2) 1:1 격리 구조 (Isolation)

* 호스트 내부에는 여러 개의 클라이언트가 존재할 수 있지만, 클라이언트 1개는 오직 서버 1개하고만 연결(1:1)됩니다.
* **이점:** 서버끼리 서로의 응답이나 데이터에 직접 접근할 수 없으므로, 인사 DB 서버가 문서 검색 서버의 데이터를 몰래 읽는 등의 **보안 사고를 구조적으로 방지**합니다.

---

### 3) 소형 마이크로 서버 (Micro-Server) 관례

* 사내 모든 시스템을 1개의 거대한 MCP 서버로 통째로 만드는 것이 아니라, `파일 서버`, `DB 서버`, `Slack 서버`처럼 **기능 단위로 작게 분리**해서 만듭니다.
* **이점:** 사용자나 에이전트별로 "DB 접근 권한만 부여", "파일 접근 권한은 제한"과 같이 **세밀한 권한 제어가 용이**해집니다.
