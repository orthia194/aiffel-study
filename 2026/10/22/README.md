# ⚡ 벡터 데이터베이스(Vector DB) 심층 아키텍처 및 검색 최적화 가이드
> Qdrant와 HNSW 알고리즘을 기반으로 한 벡터 인덱싱, 페이로드 필터링, 양자화(SQ/BQ), 멀티벡터(Multi-Vector) 설계 및 실무 배포 전략

## 🧭 1. HNSW (Hierarchical Navigable Small World) 핵심 메커니즘

HNSW는 수백만 개의 고차원 임베딩 벡터 속에서 가장 유사한 이웃(ANN)을 0.001초 만에 찾아내는 **계층형 그래프 기반 알고리즘**입니다.

[Layer 2 (고속도로)] ● ───────────────────────────> ● (대구역 초고속 워프) │ [Layer 1 (국 도)]
● ─────────> ● ─────────> ● (도시 단위 좁히기) │ [Layer 0 (골목길)]
●───●───●───●───●───●───●───● (목적지 근처 촘촘한 정밀 탐색)


### 3대 핵심 파라미터와 튜닝 원칙
* **`M` (노드당 최대 간선 수):**
  * 각 벡터가 가질 연결선의 개수. CPU 캐시 라인(64B)과 메모리 정렬을 고려해 관례적으로 $2^n$ 단위(`8, 16, 32, 64`)를 사용.
  * $M$이 커질수록 그래프가 촘촘해져 정확도(Recall)가 오르지만, **RAM 메모리 사용량이 정비례하여 증가**.
* **`ef_construct` (인덱스 구축 시 탐색 후보 수):**
  * 인덱스를 처음 지을 때 살펴보는 우선순위 큐(Heap)의 깊이 (기본값: `100 ~ 200`).
  * 클수록 인덱싱 시간은 길어지지만 그래프 품질이 극대화됨.
* **`efSearch / ef` (검색 시 탐색 후보 수):**
  * 질의할 때 임시 장바구니에 담아둘 후보군 크기 (기본값: `50 ~ 128`).
  * $ef \ge k$ 여야 하며, 키울수록 정확도가 상승하고 속도는 소폭 감소.

> 💡 **수확 체감(Diminishing Returns)의 법칙:**  
> 데이터 규모가 수천~수만 건 수준일 때는 $M=8$만으로도 정답률 99%에 도달(포화 상태)하므로, 무조건 큰 파라미터를 쓰기보다 **데이터 규모에 맞춰 최소한의 $M$으로 메모리를 아끼는 것**이 실무의 핵심입니다.

## 🚧 2. 벡터 검색 필터링의 역설과 페이로드 인덱스(Payload Index)

### 필터 검색의 역설 (RDB vs Vector DB)
* **일반 SQL (MySQL):** `WHERE` 조건을 붙이면 탐색 범위가 줄어들어 **속도가 빨라짐**.
* **벡터 DB (HNSW):** 메타데이터 필터를 붙이면 **오히려 속도가 3배 이상 느려짐 (`2.89 ms` ➔ `8.97 ms`)**.

[인덱스 없는 필터 검색] ➔ "미로 속에 방벽이 떨어지는 현상" 출발 ──> 🚧방벽(조건 불일치) ➔ 후진(Backtracking) ➔ 🚧방벽
➔ 우회 탐색 ➔ 지연 급증!

  - 치명적 위험: 정답 노드가 방벽에 완전히 둘러싸이면 탐색이 조기 포기되어 결과를 못 채움(고립된 섬 버그).


### 해결책 : 페이로드 인덱스 (Payload Index)
* 사전 메타데이터 색인(B-Tree / Inverted Index)을 생성하여 탐색기에게 **'방벽 지름길 지도'**를 제공:
  ```python
  qc.create_payload_index(collection_name="docs_base", field_name="dept", field_schema=PayloadSchemaType.KEYWORD)

  - 결과: 일일이 노드 대문을 열어보지 않고 조건에 맞는 노드로 직행하여 지연 시간이 8.97 ms ➔ 2.49 ms로 4배 단축.

🗜️ 3. 벡터 양자화(Quantization)와 재점수화(Rescoring)

대규모 검색에서 RAM 비용을 절감하기 위한 압축 기술입니다.

| 구분                    | 비트 수      | 용량 압축률            | 기본 정밀도           | 권장 사용 시나리오                     |
| :-------------------- | :-------: | :---------------: | :--------------: | :----------------------------- |
| **Float32 (Base)**    | 32-bit    | 1배 (기준)           | 100%             | 수만 건 이하, 최고 정밀도가 필요할 때         |
| **SQ (Scalar / SQ8)** | **8-bit** | **4배 압축 (1/4)**   | **98\~99% (우수)** | **실무 엔터프라이즈 RAG의 1순위 표준 세팅 ⭐** |
| **BQ (Binary)**       | **1-bit** | **32배 압축 (1/32)** | 4% (붕괴)          | BQ 전용 학습 모델 + 초거대 규모           |

이진 양자화(BQ)의 복원 공식 : 오버샘플링 + 재점수화 (Rescoring)

  - 문제: 32비트 소수점을 1비트(0 또는 1)로 깎으면 해상도가 뭉개져 **놓치는 비율이 0.960(96% 오답)**으로 치솟음.
  - 오버샘플링(Oversampling):
      - 최종 k=10개를 원할 때, 1차 이진 탐색에서는 4배수(40개)를 넉넉하게 쓸어 담음.
  - 재점수화(Rescoring):
      - 디스크에 보관해 둔 원본 Float32 벡터로 오버샘플링된 후보들만 핀포인트 재채점.
  - 실측 결과:
      - k=30 확장 시 오버샘플링 4배 적용으로 오답률 0.956 ➔ 0.448로 수직 낙하 (적중률 55% 돌파).
      - 계산량 증가에도 불구하고 검색 지연 시간은 2.61 ms ➔ 2.73 ms로 고작 0.12ms 증가에 그침 (압도적 가성비).

## 🎯 4. 고정밀 RAG를 위한 멀티벡터(Multi-Vector) 저장 설계

긴 문서를 단 1개의 벡터로 평균 내어 압축할 때 발생하는 **'문맥 희석(과일 주스 현상)'**을 해결하는 최신 ColBERT 스타일 지연
상호작용(Late Interaction) 기법입니다.

[문서 1개 저장 구조]
PointStruct(
    id = "doc_001",
    vector = {
        "summary": [1024차원 단일 요약 벡터],          # 👈 1단계 광속 필터용 (HNSW 적용)
        "parts":   [[1번 문장], [2번 문장], [3번 문장]]  # 👈 2단계 정밀 타격용 (hnsw_config: m=0)
    }
)

2단계 검색 파이프라인 (Prefetch ➔ MaxSim)

1.  1단계 Prefetch (요약 기반):
    Prefetch(query=qv, using="summary", limit=100)
    가벼운 요약 벡터로 전사 문서 중 유력 후보 100개를 2.29 ms 만에 선발.
2.  2단계 MaxSim 재채점 (문장 기반):
    MultiVectorComparator.MAX_SIM
    선발된 100개 문서의 세부 문장 조각들과 질문을 1:1 대조하여 가장 높은 유사도를 합산.
3.  성능 실측치:
      - 검색 지연 시간: 3.41 ms (단일 벡터 대비 불과 1.1ms 증가로 문장 단위 정밀 타격 달성).
      - 저장 용량: 문장 조각이 3배(7,500개) 늘었음에도 조각 벡터에 그래프 생략(m=0) 묘수를 적용하여 용량 증가는 50%
        수준(344MB ➔ 516MB)으로 방어.

## 🏗️ 5. [추가 지식] 실무 프로덕션 배포 및 운영 노하우

① RAM 용량 산정 공식 (Capacity Planning)

프로덕션 서버를 발주하기 전, 필요한 RAM 용량을 사전에 계산하는 실무 공식입니다:

\text{RAM 크기} \approx N \times \left( \text{차원수} \times \text{바이트} + M \times 8\text{ bytes} \right) \times 1.3\text{ (안전 여유율)}

  - 예: 100만 건(10^6), 768차원, M=16 기준
      - Float32 (4바이트):
        10^6 \times (768 \times 4 + 16 \times 8) \times 1.3 \approx \mathbf{4.16\text{ GB}}
      - SQ8 양자화 (1바이트):
        10^6 \times (768 \times 1 + 16 \times 8) \times 1.3 \approx \mathbf{1.16\text{ GB}}
        (약 72% 절감)

② 밀집 벡터의 맹점과 하이브리드 검색 (Dense + Sparse/BM25)

  - 밀집 벡터(Dense)의 한계: 의미는 잘 파악하지만, "제3조", "010-1234", "PRJ-2026-X" 같은 고유 식별자나 특수
    키워드 검색에서 취약.
  - 해결책 (RRF, Reciprocal Rank Fusion):
      - 의미 검색(BGE-M3 Dense)과 키워드 검색(BM25/Sparse)을 동시에 수행한 뒤, 순위를 역수로 환산하여
        결합(\text{Score} = \frac{1}{60 + \text{Rank}_{\text{dense}}} + \frac{1}{60 + \text{Rank}_{\text{sparse}}}).

③ 무중단 재인덱싱 배포 (Alias Switching)

실무에서는 운영 중인 컬렉션을 직접 수정하지 않고 **'별칭(Alias)'**을 통해 무중단으로 전환합니다:

[운영 챗봇] ──> Alias: "docs_live" ──> [컬렉션 docs_v1 (현재 운영 중)]

(새벽 3시 백그라운드에서 docs_v2 인덱싱 & 게이트 검증 완료)
                                              │
[운영 챗봇] ──> Alias: "docs_live" ───────────┴──> [컬렉션 docs_v2 (0초 스위칭!)]

  - 새 인덱스(docs_v2)를 백그라운드에서 완벽히 빌드하고, 배포 게이트(Deploy Gate) 검증을 통과하는 순간 별칭
    포인터를 0.001초 만에 원자적(Atomic)으로 스위칭하여 다운타임 0초 달성.
