## 📌 1. RAG를 배우기 전 제미나이와 나눈 RAG 핵심 요약

**RAG란?**
* AI가 암기한 지식(가중치)으로만 답하는 대신, 외부 자료(DB, 문서)를 **실시간으로 찾아 읽고(Retrieval)** 답변을 생성(Generation)하는 기술입니다.


**왜 쓸까?**
* 하루가 다르게 바뀌는 최신 정보나 코드를 매번 비용(수억~수십억 원)을 들여 파인튜닝(학습)할 수 없기 때문입니다.


**데이터 저장 방식 (Chunking & Syntax)**
* 코드는 1줄씩 나누지 않고 **5~20줄 분량의 '의미 있는 덩어리(Chunk)'** 단위로 저장합니다.
* 줄바꿈(`\n`)이나 들여쓰기 같은 문법 요소는 100% 보존된 상태로 저장됩니다.


**DB의 종류 (일반 DB vs AI 전용 DB)**
* **서버 폴더의 `.txt`/`Word` 파일:** 규모가 작다면 직접 읽어서 넘겨주어도 잘 작동합니다.
* **MariaDB:** 단어 철자가 일치해야 검색되는 **키워드 검색** 방식입니다.
* **Vector DB (AI 전용 DB):** 단어가 달라도 문맥과 뜻이 비슷하면 찾아오는 **의미(Semantic) 검색** 방식입니다.

## 💡 2. RAG에 대해 추가로 알면 좋은 핵심 3가지

### ① 임베딩(Embedding): 글자를 숫자로 바꾸는 과정

RAG가 작동하려면 "텍스트 ➔ 숫자의 배열(Vector)"로 바꿔주는 변환기가 필요한데, 이를 임베딩 모델(Embedding Model)이라고 부릅니다.

> 예: `"강아지"` ➔ `[0.12, -0.45, 0.88, ...]`
> `"멍멍이"` ➔ `[0.11, -0.44, 0.89, ...]` *(숫자가 거의 비슷함 ➔ 연관어 판단)*

Vector DB에 저장하거나 검색할 때는 항상 이 임베딩 모델을 거쳐 숫자로 변환된 좌표를 비교하게 됩니다.

---

### ② 랭킹/재정렬 (Re-ranking): 더 똑똑한 참고자료 뽑기

Vector DB가 유사한 텍스트 덩어리를 10개 찾아왔다고 해서 10개를 다 AI에게 주면, 읽느라 속도가 느려지고 비용(토큰)도 많이 듭니다.
그래서 **Re-ranker**라는 별도의 소형 AI 모델을 중간에 두어, 10개 중 **질문과 가장 진짜 밀접한 TOP 3개만 딱 추려서 프롬프트에 넘겨주는 테크닉**을 필수적으로 조합합니다.

---

### ③ RAG vs Fine-tuning(SFT) 역할 분담

많은 개발자가 두 개념을 혼동하는데, 간단히 구분하면 다음과 같습니다.

| 구분 | Fine-tuning (SFT) | RAG (검색 증강) |
| --- | --- | --- |
| **비유** | **말투/말귀/역할 배우기** | **오픈북 시험 (백과사전)** |
| **역할** | AI의 말투, 문체, 특정 정답 포맷, 말투 습관 변경 | 최신 정보, 내부 보안 문서, 변경되는 코드 참조 |
| **적합한 상황** | "말투를 의사처럼 바꿔줘", "JSON 형식을 잘 지키게 해줘" | "우리 회사 최신 규정 알려줘", "최신 API 코드로 짜줘" |

> 💡 **실무 트렌드:** SFT로 "말귀를 잘 알아듣고 가공을 잘하는 AI 뇌"를 만든 뒤, 그 AI에 RAG를 붙여서 최신 문서를 읽게 하는 **조합 방식**을 가장 선호합니다.

---

### 📌 최종 한 줄 정리

> RAG는 **`임베딩(글자➔숫자 변환)`**을 통해 **`Vector DB`**에 코드를 덩어리(`\n` 포함)째 넣어두고, 질문이 들어오면 **`가장 유사한 덩어리를 찾아 프롬프트에 얹어 답하게 만드는 기술`**입니다!

---

### 1. Data Preparation (데이터 준비 단계: 사전 작업)

외부 문서를 LLM이 검색할 수 있는 수치 데이터(Vector)로 바꿔 DB에 저장하는 오프라인 과정입니다.

1. **Information Extraction (정보 추출):** PDF, 웹, OCR 등의 파일에서 순수 텍스트를 추출합니다.


2. **Chunking (청킹):** 길고 복잡한 글을 500~1,000자 단위의 의미 있는 조각(Chunk)으로 분할합니다.


3. **Embedding (임베딩):** 분할된 텍스트 조각을 임베딩 모델에 통과시켜 고차원의 **의미적 벡터 수치**로 변환합니다.


4. **Vector DB Storage (저장):** 변환된 벡터를 Pinecone, pgvector 등 유사도 검색에 특화된 Vector DB에 인덱싱하여 저장합니다.



---

### 2. Retrieval & Generation (검색 및 생성 단계: 실시간 처리)

사용자가 질문을 보냈을 때 실시간으로 최적의 답을 찾아내는 온라인 과정입니다.

1. **Query Embedding (질문 임베딩):** 사용자 질문을 데이터 준비 때와 **동일한 임베딩 모델**로 벡터 변환합니다.


2. **Vector Search (유사도 검색):** Vector DB에서 질문 벡터와 가장 가까운(코사인 유사도 등) 상위 $K$개(Top-K) 문서 조각을 초고속으로 추려냅니다.


3. **Prompt Augmentation (프롬프트 합성):** 추출한 관련 문서 조각들(Context)과 원본 질문(Query)을 합쳐 LLM 전달용 프롬프트를 만듭니다.


4. **Response Generation (답변 생성):** LLM이 제공된 문서를 근거로 환각(Hallucination) 없이 정확한 답변을 생성하여 출력합니다.


---

### 3. 일반 DB 대신 Vector DB & 임베딩을 쓰는 이유

| 구분 | 일반 DB (Relational DB) | Vector DB (임베딩 검색) |
| --- | --- | --- |
| **검색 방식** | 키워드/단어 완전 일치 (LIKE 검색) | 의미/문맥 유사도 검색 (Semantic Search) |
| **단어 불일치** | '연봉' 검색 시 '급여 인상' 문서 못 찾음 | 단어가 달라도 맥락이 같으면 **정확히 탐색** |
| **대용량 속도** | 데이터가 커지면 Full Scan으로 속도 급감 | ANN(고속 근사 탐색) 알고리즘으로 **초고속 유지** |

* **핵심 목적:** 사람이 말하는 "의미와 문맥"을 파악해서 정확한 문서를 찾고, 수백만 건의 데이터 속에서도 "미친 속도(ms 단위)"를 확보하기 위함입니다.
