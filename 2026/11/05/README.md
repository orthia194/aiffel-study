### 1. 한 줄 비유: 두 기술의 본질

* **KV 캐시:** *"지난번에 한 말을 까먹지 않으려고 **수첩에 적어두는 행위**"*  
  $\to$ **알고리즘 최적화** (다음 토큰을 만들 때 과거 문맥의 중복 계산을 없앰)
* **플래시 어텐션:** *"수첩을 펼쳐 읽고 연산할 때 **암산(SRAM 캐시)으로 초고속 처리하는 기법**"*  
  $\to$ **하드웨어 최적화** (GPU의 느린 VRAM 왕복을 없애고 SRAM 안에서 한 번에 끝냄)

---

### 2. KV 캐시 (KV Cache) 요약

1. **목적과 효과:**
   * 새 토큰을 1개 생성할 때마다 이전 토큰들을 처음부터 다시 계산($O(N^2)$)하지 않고, 미리 계산해 둔 Key/Value 텐서를 재사용하여 **생성 속도를 대폭 단축**시킵니다. *(실험에서 약 4.6배 속도 향상 확인)*
2. **메모리 특성 (Where & How much):**
   * 컴퓨터 RAM이 아니라 **GPU VRAM**에 직접 상주합니다.
   * 시퀀스 길이에 **정확히 선형($O(N)$)으로 비례**하여 증가합니다.
   * *실측치 (Qwen2.5-1.5B 기준):* 256 토큰 = 7 MiB $\to$ **1,024 토큰 = 28 MiB**
3. **주의할 점:**
   * 대화가 길어지거나 동시 접속자 수가 늘어나면 VRAM을 점점 갉아먹으므로, VRAM의 여유 공간을 계산해 **최대 토큰 상한선(Context Window Limit)**을 걸어두어야 합니다.

---

### 3. 플래시 어텐션 (FlashAttention) 요약

1. **해결한 문제 (Memory-Bound 병목):**
   * 기존 셀프 어텐션은 거대한 $N \times N$ 관계도 행렬을 느린 **HBM(VRAM)**에 썼다 읽느라 GPU 연산 코어가 놀게 되는 병목이 있었습니다.
2. **핵심 원리 (3가지 기둥):**
   * **타일링 (Tiling):** 데이터를 코어 바로 옆의 초고속 캐시(**SRAM**) 크기에 맞춰 블록 단위로 쪼개어 가져옴.
   * **온라인 소프트맥스 (Online Softmax):** 전체 데이터를 다 보지 않고도 블록 단위로 즉석에서 보정(Rescaling)하며 소프트맥스 누적합을 구함 $\to$ **$N \times N$ 행렬을 VRAM에 아예 만들지 않음.**
   * **역전파 시 재계산 (Recomputation):** 학습 시 $N \times N$ 행렬을 저장하지 않고 버린 뒤, 역전파 때 SRAM 안에서 빠르게 다시 계산 $\to$ 메모리 점유 $O(N^2) \to \mathbf{O(N)}$ 급감.
3. **가장 큰 장점:**
   * 희소 어텐션(Sparse)처럼 대충 건너뛰는 게 아니라, 수학적으로 **100% 동일한 결과(Exact Attention)**를 내면서도 **속도는 2~4배 빠르고 메모리는 획기적으로 절약**됩니다.

---

### 4. 두 기술이 함께 일하는 2단계 생애주기

실제 챗봇이 돌아갈 때 두 기술은 완벽한 콤비로 동작합니다.

```
[1단계: Prefill (프롬프트 입력 처리)]
 • 긴 질문을 한 번에 읽음 (병렬 연산)
 • FlashAttention 활약: 거대한 $N \times N$ 행렬 생성을 막아 VRAM 순간 폭발(Spike OOM) 방지
 • KV Cache 활약: 계산된 질문 토큰들의 Key, Value를 캐시에 '미리 채워둠(Pre-fill)'
      │
      ▼
[2단계: Decode (답변 텍스트 생성)]
 • 토큰을 1개씩 순차적으로 생성 (타자기 효과)
 • KV Cache 활약: 과거 문맥을 다시 계산하지 않고 캐시에서 꺼내 씀 (속도 수 배 가속)
 • FlashDecoding 활약: 새로 만든 1개 토큰과 수천 개의 KV 캐시를 고속으로 결합 연산
```

### 5. 8GB VRAM 실전 운영 핵심 수칙

1. **VRAM 가계부의 60~70% 룰:**
   * 모델 가중치만 보고 VRAM을 꽉 채우면 안 됩니다.
   * **8GB VRAM 기준:** 모델 가중치는 **최대 4.5~5GB 수준(4-bit 양자화 모델 등)**으로 맞추고, **남은 3GB는 KV 캐시와 Prefill 활성화 텐서용 숨구멍**으로 비워두어야 OOM을 피할 수 있습니다.
2. **GPU 낭비 방지 (StoppingCriteria):**
   * 사용자가 스트리밍 도중 창을 닫거나 '중지'를 누르면 백엔드에 즉각 취소 신호를 보내야 합니다. (신호가 없으면 90토큰 이상 백그라운드에서 헛돌며 GPU를 점유함)
3. **OOM 방어선 구축:**
   * **사전 예방(Guardrail):** 모델에 넣기 전 프롬프트 길이를 토크나이저로 사전 검사하여 안전 한도를 넘으면 입력을 거절.
   * **사후 복구(Soft Recovery):** `try...except torch.cuda.OutOfMemoryError`로 감싸고 `gc.collect()` + `torch.cuda.empty_cache()`를 실행하여 서버 다운 없이 안전하게 실패 안내 메시지 반환.
