# ⚡ LLM RAG 서빙 최적화 & 병목 분석 실습

> **핵심 질문:** *"모델의 생성 속도를 높였는데도 RAG 답변이 늦다면 어느 단계부터 확인해야 합니까?"*

사내 규정 안내 RAG 챗봇을 대상으로 **구간별 지연 시간(Latency) 측정**, **캐시·보안(권한)·프롬프트 순서 실험**, **모델 라우팅 및 폴백**, **회귀(Flip) 방지 설정 선택**까지 RAG 서빙 파이프라인 전반을 검증한 기록입니다.

---

## 📌 한눈에 보는 결론

* **최대 병목은 LLM 생성이 아니라 앞단의 `리랭크(재정렬)` 단계였습니다.**
  * 기준선 전체 응답 시간(중앙값 `4,996ms`) 중 **CPU 기반 리랭크가 `3,218ms` (`60.8%`)** 를 차지했습니다.
  * 임베딩(`~30ms`), 벡터 검색(`~4ms`), 첫 토큰(`75~232ms`)을 아무리 최적화해도 **리랭크 후보 수(`candidates`)를 줄이지 않으면 체감 속도는 크게 줄지 않습니다.**
* **속도 최적화는 반드시 `근거적중` · `정답률` · `권한 격리` · `Flip(기존 정답 손실)`과 함께 검증해야 합니다.**
  * 겉보기 점수나 중앙값만 보고 설정을 바꾸면, 기존에 맞히던 문항이 깨지거나(`flip`) 타 부서 기밀이 유출되는 사고가 발생할 수 있습니다.

## 🛠 실험 환경 및 데이터셋

* **인프라**: Tesla T4 GPU (`vLLM 0.30.0`), `Qdrant v1.19.1`
* **모델 구성**
  * 생성 모델: `Qwen/Qwen2.5-1.5B-Instruct` (`big`), `Qwen/Qwen2.5-0.5B-Instruct` (`small`)
  * 임베딩 모델: `intfloat/multilingual-e5-small` (CPU, 384차원)
  * 재정렬(Reranker): `BAAI/bge-reranker-v2-m3` (CPU, FP32)
* **데이터셋**: 사내 규정 26건 (5개 부서: 공개 18 / 인사 3 / 재무 2 / 영업 2 / 보안 1)
* **평가 세트**: 25문항 (조회 14 / 계산 5 / 권한 6) + 18건 트래픽 시나리오 (`TRAFFIC`)

## 📊 1. 기준선(Baseline) 구간별 병목 측정

`Stream=True` 호출과 `Spans` 계측을 통해 요청 1건의 내부 구간을 **p50(중앙값) / p95(꼬리 지연)** 로 분리 측정했습니다.

| 구간 | 평균 비중 | p50 / p95 (ms) | 비고 |
| :--- | :---: | :---: | :--- |
| **임베딩** | 0.5% | 30 / 34 | 질문 1건 벡터화 |
| **검색 (Qdrant)** | 0.1% | 4 / 5 | 부서 권한 사전 필터링 포함 |
| **재정렬 (Rerank)** | **60.8%** | **3,218 / 3,853** | **최대 병목** (후보 20건 CPU Cross-Encoder 평가) |
| **첫 토큰 (TTFT)** | 4.2% | 232 / 279 | 프롬프트 Prefill + 첫 토큰 생성 |
| **나머지 (Decode)** | **34.4%** | **1,446 / 3,785** | 답변 토큰 생성 (`max_tokens=300`) |
| **전체 (E2E)** | 100% | **4,996 / 7,303** | **정답 `11/25` · 근거적중 `25/25`** |

> 💡 **진단:** `근거적중 25/25`로 검색 품질은 완벽했으나, 1.5B 모델의 추론·형식 오류로 정답은 `11/25`에 머물렀으며, 전체 시간의 60% 이상이 리랭크에서 소모되고 있었습니다.

## 🧪 2. 주요 실험 결과 비교

### ① 청크 수(`keep`) · 생성 길이 상한(`max_tokens`) 조절
| 설정 | 입력 토큰 | 전체 p50 / p95 (ms) | 정답 | 근거적중 | `(flip, 새로 맞힘)` |
| :--- | :---: | :---: | :---: | :---: | :--- |
| 기준선 (`keep=5, max=300`) | 741 | 4,996 / 7,303 | 11/25 | 25/25 | - |
| 청크 3개 (`keep=3`) | 587 | 4,882 / 7,499 | 13/25 | 25/25 | `(['Q25'], ['Q02', 'Q11', 'Q23'])` |
| **답 상한 120 (`max=120`)** | 741 | 4,797 / **6,677** | 11/25 | 25/25 | **`([], [])` (회귀 없음)** |
| 둘 다 적용 | 587 | 4,852 / 7,059 | 13/25 | 25/25 | `(['Q25'], ['Q02', 'Q11', 'Q23'])` |

* `keep`을 줄여도 **재정렬 후 자르기** 때문에 리랭크 시간(`~3.15s`)은 줄지 않습니다. 단, 4·5위 방해 문서가 빠져 정답 수는 소폭 상승했습니다.
* `max_tokens=120`은 정상 답변을 해치지 않으면서 장황한 꼬리 생성(`p95`)만 안전하게 잘라냈습니다.

### ② 응답 캐시 & 권한·버전 보안 (`TRAFFIC` 18문항)
| 캐시 방식 | 전체 p50 / p95 (ms) | 정답 | 타 부서 유출 | 문제점 |
| :--- | :---: | :---: | :---: | :--- |
| 캐시 없음 (기준) | 4,663 / 5,474 | 8/18 | 0 | - |
| 정확 일치 (`exact, scoped=True`) | 4,589 / 5,793 | 8/18 | 0 | 히트율 낮음(1/18) + 첫 오답 박제 위험 |
| 시맨틱 (`질문만, scoped=False`) | **32** / 6,256 | **6/18** | **3건 (유출!)** | **권한 다른 직원이 타 부서 기밀 수신** |
| 시맨틱 (`권한 포함, scoped=True`) | 4,460 / 5,885 | **6/18** | 0 | 유사 질문 오답 매칭 다수 발생 |

* **임베딩 유사도의 함정 (`0.80 ~ 0.98` 시뮬레이션):**
  * `해외 출장` ↔ `국내 출장` (**유사도 `0.986`**), `자녀 결혼` ↔ `본인 결혼` (**`0.977`**) 처럼 답이 정반대인 질문이
  * 실제 같은 뜻의 말 바꾸기(`재택근무 일주일에 며칠...`, **`0.949`**)보다 유사도가 더 높았습니다.
  * 임계값을 **`0.98`** 까지 높여도 적중한 2건이 모두 오답(`(2, 2, 0)`)이었으며, 수치·조건이 민감한 FAQ에는 단순 벡터 시맨틱 캐시가 부적합함을 확인했습니다.

### ③ 프롬프트 순서와 vLLM KV Prefix Cache (`reset_prefix_cache` 후 측정)
| 레이아웃 | 캐시 적중 토큰 비율 | 첫 토큰 p50/p95 | 전체 p50/p95 | 정답 |
| :--- | :---: | :---: | :---: | :---: |
| **`bad`** (시각·UUID 앞 배치, 질문→문서) | **1.9%** | 329 / 368 ms | 5,200 / 9,577 ms | **3/18** |
| **`good-score`** (고정 지시문 앞, 점수순) | **47.1%** | 252 / 305 ms | 4,787 / 6,176 ms | 8/18 |
| **`good-id`** (고정 지시문 앞, **문서 ID순**) | **61.6%** | **215 / 285 ms** | **4,731 / 5,388 ms** | **9/18** |

* 매 요청 변하는 시각/요청번호를 프롬프트 앞쪽에 두면 **16토큰 블록 해시 체인**이 첫 블록부터 깨져 KV 캐시 적중률이 `1.9%`로 추락합니다.
* 문서를 점수순 대신 **문서 ID 오름차순(`good-id`)** 으로 정렬하면 공통 문서 블록까지 prefix가 이어져 캐시 적중률이 `61.6%`까지 상승합니다.

### ④ 작은 모델 라우팅(`0.5B`) & 타임아웃 폴백
* **전부 작은 모델(`0.5B`)**: 조회 문항(`12/14`)은 강했으나 권한 문항(`1/6`)이 약했고, 설명을 길게 생성해 디코딩 중앙값(`1,762ms`)이 오히려 `1.5B`(`1,446ms`)보다 길어졌습니다.
* **규칙 기반 라우터(`CALC`)의 한계**: `"1박"`이 들어간 단순 조회(`Q05, Q06`)는 `big`으로 가고, `"4일"`을 쓴 계산 문항(`Q25`)은 `small`로 빠지는 경계 사례 발생.
* **타임아웃 상한(`0.19초`) + 폴백(`big → small`)**:
  * 상한만 걸면 **실패 20건(`정답 2/25`)** 으로 서비스 붕괴.
  * **`fallback=True` 적용 시 실패 0건(`정답 14/25`)** 으로 안정성 확보.

### ⑤ 심화 & 부록: 진짜 병목 해결 및 운영 패턴
* **리랭크 후보 수(`candidates`) 축소**: `근거적중 25/25`를 유지한 채 검색+재정렬 시간이 극적으로 단축됨.
  * `20개 (3,365~3,448ms)` → `10개 (1,738~1,826ms)` → `5개 (922~977ms)` → **`3개 (586~649ms, ~5.5배 단축)`**
* **문장 압축(`compress`)의 착시**: 2-gram 기반 압축 시 입력 토큰은 `741 → 652`로 줄고 `근거적중 25/25`는 유지됐지만, 핵심 문장이 잘려 **정답이 `11/25 → 7/25`로 하락**했습니다.
* **병렬화 & 사전 필터링**: 권한·이력·임베딩 병렬 조회로 앞단 시간 `103.6ms → 45.5ms` 단축. Qdrant 사전 필터링으로 권한 외 문서 혼입으로 인한 검색 결과 축소(5건→3건) 방지.
* **동시 부하(`workers 1 → 4 → 8`)**: `queue_time=0`(Continuous Batching)이어도 GPU 메모리 대역폭 경합으로 **디코드 p95가 `3,785ms → 15,140ms`로 급증**.
* **`cache_salt` 격리**: `솔트 없음(61.6%)` vs **`권한 범위별 HMAC(50.8%)`** vs `사람별(41.9%)` → 부서 권한 단위로 솔트를 나누면 보안 격리와 캐시 효율을 균형 있게 확보.
* **문서 개정 캐시 무효화(`INDEX_REV`)**: 캐시 키에 `INDEX_REV`를 포함시켜 문서 업데이트 시 O(1) 무효화(웹의 `?v=2` 캐시 버스팅과 동일 원리).

```python
CHOSEN = {**BASE_CFG, "max_tokens": 120}
```
* **결과**: `정답 11/25`, `근거적중 25/25`, `(flip, 새로 맞힘) = ([], [])`, `p95 7,303ms → 7,121ms`

## 💡 추가로 알아두면 좋은 실무 심화 포인트

1. **적응형 오버샘플링 (Cascading Retrieval)**
   * 평소 80~90% 요청은 `candidates=5`로 빠르게 처리하고, **1차 리랭크 최고 점수가 임계값 미만일 때만** `candidates=20` 또는 하이브리드 검색으로 넓혀 재시도(중복 리랭크 제외, 최대 1회 제한)하면 평균 속도와 재현율을 모두 챙길 수 있습니다.
2. **TTFT vs 디코드(TPS)의 하드웨어 병목 차이**
   * **Prefill(첫 토큰)**: 대규모 행렬 곱셈 위주라 **연산량(Compute-bound)** 영향을 받습니다(Prefix Cache가 큰 힘을 발휘하는 구간).
   * **Decode(나머지)**: 토큰 1개마다 모델 가중치와 KV 캐시를 전부 GPU 메모리에서 읽어야 하므로 **메모리 대역폭(Memory-bandwidth-bound)** 에 묶입니다. 동시 접속자가 8명으로 늘었을 때 디코드 p95가 15초로 튄 이유가 바로 이 대역폭 경합 때문입니다.
3. **리랭커 자체의 가속 옵션**
   * 오늘 실험에서는 리랭커가 `CPU / FP32`에서 실행되어 3.3초가 걸렸습니다. 실서비스에서는 **GPU(FP16) 배치 추론**, **ONNX/TensorRT 변환**, 또는 **경량 리랭커 / LLM-free Late Interaction(ColBERT 등)** 으로 교체하면 같은 `candidates=20`에서도 수십~수백 ms 단위로 줄일 수 있습니다.
4. **RAG 캐시 키 설계 & 뒤늦은 마이그레이션 방어**
   * 캐시 키는 처음부터 **`(index_rev, scope, model_id, prompt_ver, normalized_query)`** 5종을 묶어 두는 것이 안전합니다.
   * 만약 운영 중 뒤늦게 `INDEX_REV`를 도입해야 한다면: ① 기존 레코드 조회 시 `it.get("rev", 1)`로 `KeyError`를 방어하고 `INDEX_REV=2`부터 시작하며, ② 배포 직후 캐시 적중률 0%로 인한 부하 스파이크(Cold Start)를 막기 위해 인기 질문을 사전 워밍업(Warm-up)하는 것이 좋습니다.
5. **평가 지표 3분할 습관**
   * RAG 개선 시 항상 **① 검색 적중(`근거적중`) → ② 최종 품질(`정답`) → ③ 기존 정답 손실(`flip`)** 을 분리해 기록해야 *"검색은 맞았는데 모델이 틀린 건지"*, *"전체 평균은 올랐는데 핵심 질문이 깨진 건지"* 를 정확히 구분할 수 있습니다.
6. **답 캐시(Answer Cache)의 함정("오답 박제")과 실무 절충안**
   * **문제점:** 웹 캐시는 DB의 확정 데이터를 저장하지만, LLM 응답 캐시는 모델의 생성 결과(환각·계산 실수 포함)를 저장합니다. 실제로 `같은 질문 캐시` 실험에서도 첫 `Q01`에서 모델이 오답을 내자 캐시가 그 오답을 그대로 저장해 재전파(`틀린 답 1`)하는 문제가 나타났습니다.
   * **실무 해결책 (하드코딩 vs 유연성의 균형):**
     1. **고빈도 FAQ 화이트리스트 캐시:** 매일 수백 번 반복되는 상위 질문(예: 연차 일수, 출장비 한도)만 운영자가 검수해 캐시에 두고, 나머지 새로운/복합 질문은 실시간 RAG로 처리합니다.
     2. **검증 게이트 + 비동기 심판(Judge LLM) + 👎 무효화:** 출력 형식·근거 문서 존재 여부 등 기본 가드레일이나 상위 모델의 사실 검증(Faithfulness Check)을 통과한 답변만 캐시에 승격시키고, 사용자가 👎 피드백을 누르면 즉시 삭제합니다.
     3. **"최종 답" 대신 "중간 결과(리랭크 · KV Prefix)"만 캐싱:** 최종 답변 문장을 박아두지 않고 **`(권한, 질문) → 리랭크된 문서 ID 목록`** 까지만 캐싱하면, 전체 시간의 60%를 차지하던 **리랭크 병목(3.2초)은 0초로 건너뛰면서도** 최종 답변은 LLM이 후속 질문·대화 문맥에 맞춰 매번 유연하게 생성할 수 있습니다.
