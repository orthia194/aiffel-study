# 🚀 vLLM 심화 서빙 및 용량 산정(Capacity Planning) 실습 보고서

> **핵심 질문:** *동시 요청 수를 늘렸을 때, 시스템의 토큰 처리량(Throughput)과 사용자가 체감하는 지연 시간(TTFT, ITL)은 어떻게 변화하는가?*

---

## 📌 1. 실행 환경 (Environment)

* **GPU:** NVIDIA A40 (48GB VRAM / Compute Capability 8.6)
* **Model:** `Qwen/Qwen2.5-1.5B-Instruct` (약 3.09GB in BF16)
* **Framework:** `vLLM v0.30.0`, `PyTorch 2.13.0`, `Transformers 5.22.2`
* **Max Context Length:** 4,096 tokens
* **Precision:** `bfloat16`

---

## 🎯 2. 핵심 요약 및 결론 (Executive Summary)

1. **처리량과 지연의 트레이드오프:**
   * 동시성을 1에서 32까지 증가시켰을 때 전체 처리량은 **136 tok/s $\rightarrow$ 2,644 tok/s로 약 19.4배 폭발적으로 성장**함.
   * 그러나 동시성 32에서 GPU 내부 스케줄러 대기열(Queue)이 생기며 **최악의 첫 토큰 지연 시간(p99 TTFT)이 5배 이상 급증**함.
2. **이론 용량과 서비스 한계의 불일치:**
   * A40 VRAM 메모리 계산상으로는 **최대 335명**의 동시 요청을 담을 수 있지만, 실제 **서비스 수준 목표(SLO: p99 TTFT < 2.0s, ITL < 0.1s)**를 지키는 운영 한계선은 **동시성 16~32 수준**임.
3. **황금률:** **"모두를 한꺼번에 들여보내 다 같이 지연을 겪는 것보다, 입장 제어(Admission Control)를 통해 순서대로 초고속 처리하는 것이 전체 시스템 효율이 압도적으로 높다."**

## 🔬 3. 주요 실험 및 실측 결과 (Experiments)

### Test 1. 동시성 스윕과 운영점(Operating Point) 도출
동시 요청 수를 늘려가며 vLLM 내장 벤치마크 및 비동기 스트리밍 호출을 수행했습니다.

| 동시성 | 완료 | 실패 | 출력 토큰/초 | ttft p50 (ms) | ttft p99 (ms) | itl p99 (ms) | Goodput (req/s) | 대기열 최고 | 비고 |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| **1** | 16 | 0 | 136 | 46 | 102 | 12 | 1.06 | 0 | 선형 증가 구간 |
| **4** | 32 | 0 | 513 | 83 | 103 | 12 | 4.01 | 0 | |
| **16** | 128 | 0 | 1,637 | 199 | 318 | 24 | 12.79 | 7 | 권장 운영점 |
| **32** | 256 | 0 | 2,644 | 193 | 577 | 65 | 20.66 | 14 | 무릎(Knee) 지점 |

* **무릎 지점(Knee Point):** 동시성 32 (처리량 증가율 둔화 시작)
* **SLO 통과 운영점:** 동시성 16~32 (p99 TTFT $\le$ 2,000ms, p99 ITL $\le$ 100ms 만족)

### Test 2. KV 캐시 고갈과 선점(Preemption) 재연산 참사
`--num-gpu-blocks-override 128` (총 2,048토큰만 허용)로 극단적 메모리 제약을 가한 후 과부하를 주입했습니다.

```
[보통 서버]  선점:  0회 | KV 최고:   0% | 처리량: 1,007 tok/s | e2e p99: 4.2초
[좁은 서버]  선점: 28회 | KV 최고: 100% | 처리량:   756 tok/s | e2e p99: 5.5초
```
* **인사이트:**
  * KV 공간이 꽉 차자 서버 OOM 방지를 위해 활성 요청을 강제로 쫓아내는 **선점(Preemption)**이 28회(요청당 1.75회) 발생함.
  * 쫓겨났던 요청이 복귀할 때 이미 계산했던 토큰을 **GPU가 다시 Prefill 재연산(Recomputation)하면서 연산력(FLOPs) 낭비와 25%의 처리량 급감**을 초래함.

---

### Test 3. 프롬프트 구조와 자동 프리픽스 캐싱(APC) 효율
동일한 규정 본문(RAG 컨텍스트)과 질문으로 구성된 프롬프트의 **배치 순서**에 따른 캐시 적중률(Hit Rate)을 측정했습니다.

| 순서 | 프롬프트 구조 | 예측 적중률 | 실측 적중률 (지표) | API 반환 적중률 | 고찰 |
| :---: | :--- | :---: | :---: | :---: | :--- |
| **A** | `[시스템] + [규정 본문] + [질문]` | **76%** | **76%** | **76%** | 정적 컨텍스트가 맨 앞에 배치되어 완벽 재사용 |
| **B** | `[질문] + [시스템] + [규정 본문]` | **0%** | **0%** | **0%** | 맨 앞 글자가 달라 뒤쪽 전체 캐시가 무효화됨 |
| **C** | `[현재시각] + [시스템] + [규정 본문]` | **2%** | **2%** | **2%** | 초 단위 타임스탬프가 앞을 가로막아 단 1블록만 히트 |

* **Radix Tree 캐싱 법칙:** 
  $$\text{Cached Tokens} = \left( \frac{\min(\text{Common Prefix}, \text{Len} - 1)}{\text{Block Size}(16)} \right) \times 16$$
  * 변동되는 동적 데이터(시각, 사용자 ID)는 반드시 맨 뒤(질문 근처)에 두어야 수천 토큰의 프리필 비용을 아낄 수 있음.

### Test 4. 용량 보고서 3대 수치 (Capacity Planning)
수학적 메모리 공식, 엔진 초기화 로그, 실측 벤치마크 데이터를 통합 분석했습니다.

* **토큰 1개당 KV 캐시 크기 (Qwen2.5-1.5B 기준 GQA 적용):**
  $$2(\text{K,V}) \times 28(\text{Layers}) \times 2(\text{KV Heads}) \times 128(\text{Head Dim}) \times 2(\text{Bytes}) = \mathbf{28,672\text{ Bytes/Token}}$$

```json
{
  "세_숫자": {
    "계산한_동시수": 335.31,
    "엔진이_잡은_동시수": 339.36,
    "약속을_지킨_동시수": 32
  },
  "최종_서비스_한계": 32
}
```
* **결론:** 메모리 물리 한계(335명)를 기준으로 아키텍처를 설계하면 지연 시간 폭발로 장애가 발생함. **프로덕션 사이징의 기준은 항상 실측 Goodput(SLO 통과 동시성)의 최솟값(32명)**이어야 함.

## 💡 4. 프로덕션 엔지니어가 반드시 알아야 할 추가 지식

### 1) 선두 차단(Head-of-Line Blocking)과 Chunked Prefill
* **문제:** 긴 프롬프트(8,000토큰)를 가진 요청이 들어오면 GPU가 이를 한 번에 계산하느라, 이미 1글자씩 스트리밍 중이던 다른 사용자들의 디코딩(Decode)이 멈추는 **버벅임(ITL 급증)**이 발생합니다.
* **해결책 (`--enable-chunked-prefill`):**
  * 거대한 Prefill을 작은 덩어리(예: 512토큰)로 쪼개어, 매 스텝마다 `[청크 프리필 512개] + [기존 사용자 디코드 1토큰]`을 함께 연산합니다. 짧은 질문 사용자들의 스트리밍 체감 품질을 방어하는 핵심 기법입니다.

### 2) PagedAttention의 내부 블록 단편화 (Internal Fragmentation)
* vLLM은 토큰을 **16개 단위의 블록(Block)**으로 묶어 할당합니다.
* 만약 문장이 17토큰으로 끝나면 2번째 블록은 1토큰만 쓰고 15토큰 공간이 낭비됩니다.
* 따라서 프리픽스 캐싱 설계 시 **공통 프롬프트의 길이를 가급적 16의 배수에 가깝게 정렬**하는 것이 캐시 낭비를 줄이는 팁입니다.

### 3) 입장 제어(Admission Control) 아키텍처
* **vLLM 내부 방어:** `--max-num-seqs`를 안전 동시성(예: 32)으로 설정하여 GPU 내부 선점을 차단.
* **API Gateway 외부 방어:** Nginx나 Kong 같은 앞단 게이트웨이에서 토큰 버킷 알고리즘 기반 Rate Limiting을 걸어, 초과 트래픽 발생 시 즉각 **`HTTP 429 Too Many Requests`와 함께 `Retry-After: 2` 헤더를 반환**하거나 가상 대기열 화면으로 유도해야 시스템 붕괴를 막을 수 있습니다.

### 4) LoRA 서빙 용어 명확화
* **Multi-Tenant LoRA Serving (vLLM `--enable-lora`):** 베이스 모델 1벌을 띄워두고, 요청마다 서로 다른 어댑터를 한 배치 안에서 동적으로 골라 처리함 (인프라 절감).
* **LoRA Merge (`merge_and_unload()`):** 베이스 모델 가중치에 LoRA를 수학적으로 영구 결합하여 일반 단일 모델로 변환 (추론 속도 100% 복구, 어댑터 교체 불가).
* **LoRA Composition:** 여러 전문 LoRA(번역+코딩+말투)의 가중치를 융합하여 1개의 요청에 동시 적용.
