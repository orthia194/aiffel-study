## 1. 부동소수점 정밀도: FP16 vs BF16

트랜스포머 모델 학습/추론 시 메모리 사용량을 줄이기 위해 사용하는 대표적인 16비트 포맷 비교.

| 데이터 타입 | 전체 비트 | 부호(Sign) | 지수부(Exponent, 범위) | 가수부(Fraction, 정밀도) | 최댓값 | 비고 |
| :--- | :---: | :---: | :---: | :---: | :---: | :--- |
| **FP32** | 32-bit | 1 | 8 | 23 | $\approx 3.4 \times 10^{38}$ | 단정밀도 표준 |
| **FP16** | 16-bit | 1 | **5** | **10** | $\approx 65,504$ | 정밀도 높음, 오버플로 위험 (Loss Scaling 필수) |
| **BF16** | 16-bit | 1 | **8** | **7** | $\approx 3.4 \times 10^{38}$ | **FP32와 동일한 범위**, LLM 사전학습의 표준 |

* **트랜스포머에서 BF16이 대세가 된 이유:**  
  Softmax 및 Attention 계산 시 값이 치솟는 이상치(Activation Outlier)가 발생해도 오버플로(`Inf`/`NaN`)가 발생하지 않아 수치적 안정성이 압도적임.
* **하드웨어 제약:**  
  * **FP16:** Volta(V100), Turing(T4) 등 구형 GPU에서도 지원.
  * **BF16:** Ampere(A100, RTX 30시리즈) 이상 최신 하드웨어에서만 네이티브 가속 지원. (T4에서는 에뮬레이션으로 돌아가 속도 저하 발생)

## 2. QLoRA와 이중 양자화(Double Quantization)

### (1) 양자화 상수(Scale Factor)의 이해
* **FP16/BF16 원본 모델:** 숫자 자체에 지수부(크기 정보)가 포함되어 있어 **별도의 스케일 상수가 없음** (순수 16비트).
* **4-bit 양자화:** 숫자가 16가지($-8 \sim 7$) 단계로 굳어지므로, 원래 실수로 복원하기 위해 **블록(보통 64개)마다 곱해줄 양자화 상수(FP32)**가 필수적임.

### (2) QLoRA의 이중 양자화(Double Quantization) 원리
1. **1차 양자화:** 모델 가중치(16-bit) $\rightarrow$ **4-bit (NF4)** (블록 크기 64)
   * 64개마다 32-bit 상수가 붙으므로, 상수 용량만 파라미터당 **0.5 bit** 추가 낭비 ($32 / 64 = 0.5$).
2. **2차 양자화 (상수의 양자화):** 1차 양자화 상수(FP32) $\rightarrow$ **8-bit (FP8)**
   * 상수는 가중치 64개를 총괄하므로 4비트로 줄이면 오차가 극심해짐. 성능 저하가 없는 마지노선인 **8비트(FP8)**로 압축!
   * 상수의 오버헤드가 **0.5 bit $\rightarrow$ 약 0.127 bit**로 급감 (파라미터당 0.37 bit 절약).

> 💡 **8비트 양자화(INT8)는 왜 이중 양자화를 안 할까?**  
> 8비트는 보통 행(Row) 전체(예: 4,096개)에 상수 1개를 두기 때문에, 상수가 차지하는 메모리 비중이 0.007 bit 수준으로 극히 미미하여 굳이 상수를 또 압축할 필요가 없음.

## 3. 양자화 오차 및 LLM 서빙 품질 검증 실습

### (1) 기초 수학 실험: 이상치(Outlier)의 파괴력
* 정상 데이터에 `60.0`이라는 이상치 1개가 섞이자, **단순 4비트 양자화에서는 8개 중 6개 값(75%)이 0으로 삭제(Underflow)**됨 (복원 오차 4.27).
* 텐서를 통째로 양자화하면 이상치 하나가 전체를 오염시키므로, QLoRA처럼 **블록(64개) 단위로 쪼개는 것(Grouped Quantization)**이 필수적임.

### (2) 16비트 vs NF4 실측 결과 (`Qwen2.5-1.5B-Instruct`, Tesla T4)

| 지표 | 16-bit (기준선) | 4-bit (NF4) | 평가 및 현상 |
| :--- | :---: | :---: | :--- |
| **가중치 메모리 (VRAM)** | 3.09 GB | **1.16 GB** | **62.5% 절감 성공** (목표 20% 초과) |
| **추론 속도 (TPS)** | **25.6 TPS** | 18.3 TPS | **28.5% 속도 저하 발생 (역양자화 오버헤드)** |
| **30문항 정답률** | **19 / 30 (63.3%)** | 13 / 30 (43.3%) | 정답 수 6개 감소 (지능 퇴행) |
| **문항 변화 (`count_flips`)** | - | **맞$\rightarrow$틀: 7개** / 틀$\rightarrow$맞: 1개 | 심각한 신규 오답 발생 |
| **최종 판정 (`review_pair`)** | - | **`[교체 보류]`** | **운영 배포 불가 판정** |

### (3) "오 좋네? 하고 덜컥 바꿨을 때" 발생하는 3대 결함
1. **JSON 포맷 지시 불이행 (D유형 5건 탈락):**  
   "JSON 한 줄로만 답하라"는 지시를 무시하고 마크다운 백틱(```` ```json ````)을 덧붙여 API 파싱 에러 유발.
2. **지문 독해 환각 (`A2`):**  
   규정의 "오후 3시"를 읽지 못하고 지문에 없는 **"17시"**를 날조.
3. **추론 속도 역설:**  
   VRAM은 절반 이하로 줄었으나, 단어 생성 시마다 16비트로 풀어내는(Dequantize) 연산 병목으로 응답 속도가 30% 느려짐.

### (4) 평가 설계의 교훈
* **평균의 함정:** 전체 총점이 비슷해도 속을 까보면 원래 풀던 문제를 틀리는(`맞→틀`) 치명적 퇴행이 숨어 있을 수 있음.
* **정규식 채점기의 한계:** `"2일이 아니라 3일입니다."`라는 문장에서 맨 앞의 `2`만 긁어가 오답을 정답 처리하는 **위양성(False Positive)**의 위험을 항상 경계해야 함.

## 4. LoRA 어댑터의 본질과 모델 머지(Merge)

### (1) 어댑터의 가중치는 몇 비트인가?
* QLoRA는 베이스 모델을 4비트로 얼려둘 뿐, **LoRA 어댑터($A, B$ 행렬)의 가중치는 처음부터 끝까지 순수한 16비트(FP16/BF16)**로 학습됨!

### (2) 모델 머지(Merge): 분배법칙을 통한 영구 합체
$$\text{Output} = (W_{원본} \times x) + (B \times A \times x) = (W_{원본} + B \times A) \times x$$
* 어댑터($B \times A$)도 16비트, 원본 본체($W_{원본}$)도 16비트이므로, **수학적으로 1:1 덧셈(+)을 통해 완전히 하나의 모델로 영구 결합**할 수 있음 (`model.merge_and_unload()`).
* **16비트 원본에 합치는 이유:** 4비트 양자화 모델에 합치면 오차가 2중으로 누적되므로, 가장 깨끗한 16비트 원본 뼈대에 합쳐 완성본을 만드는 것이 정석.

## 5. 현업 LLM 서빙 표준 아키텍처 (End-to-End)

```
[1단계: 가성비 학습]
원본 16비트 모델 ──(4-bit 압축)──> QLoRA (NF4 본체 + 16-bit LoRA 어댑터 학습)
                                         │
                                         ▼ (학습 완료 후 어댑터 가중치만 추출)

[2단계: 완성본 병합]
원본 16비트 모델 ────(1:1 덧셈 병합)────> 16-bit 완성본 모델 (Merge & Unload)
                                         │
                                         ▼

[3단계: 엔터프라이즈 서빙 (vLLM)]
  ┌── (단일 서비스 / 최대 속도 필요) ──> AWQ 4비트 압축 ──> vLLM 고속 서빙
  └── (다중 업무 / 비용 절감 필요) ───> Multi-LoRA (동적 어댑터 교체) ──> vLLM 서빙
```

1. **학습 (Training):**  
   비싼 장비 없이 일반 소비자용 GPU(RTX 3090/4090)에서 학습하기 위해 **QLoRA**를 사용한다.
2. **단일 서비스 속도 극대화 (Merge & AWQ):**  
   고객이 몰리는 단일 챗봇은 어댑터를 16비트 원본에 영구 병합(Merge)한 뒤, **AWQ** 포맷으로 다시 압축해 **vLLM**에 올려 초고속으로 서빙한다.
3. **다중 챗봇 운영 (Multi-LoRA):**  
   인사봇, 법무봇, 코딩봇 등 여러 챗봇을 한 서버에서 돌려야 할 때는 모델을 합치지 않고 베이스 모델 1대에 **어댑터를 실시간으로 USB처럼 탈부착(`--enable-lora`)**하여 VRAM 비용을 극단적으로 아낀다.

## 💡 최종 요약 (Key Takeaways)
* **QLoRA**는 저비용 고효율 **'학습용 훈련복'**이다.
* Hugging Face + `bitsandbytes` 조합 그대로 서비스를 운영하면 속도 저하와 서버 다운을 겪는다.
* 실무 배포는 반드시 검증 하네스로 회귀 문항(`맞→틀`)을 걸러내고, **모델 머지 후 AWQ 압축 또는 vLLM 엔진**을 거쳐 서빙하는 것이 표준이다.
